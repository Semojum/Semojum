# 서버 저장 계약 검토

2026-10-14 확인. 기준: [Semojum/BE commit 408e72b](https://github.com/Semojum/BE/tree/408e72bd5989d8388766cc56b4d9f1d003e0aff1). 운영 서버에 이 커밋이 배포되었는지는 검증하지 않았다.

사용자 결정: 이번 작업에서는 BE를 수정하지 않는다. 앱 구현과 아래 수정 제안만 작성한다.

## 코드에서 확인한 동작

`PageContentSaver.savePage`는 이미 있는 PageResult만 저장한다. `text`와 `braille`은 각각 독립적으로 diff를 적용한다. 기존 id면 해당 패널의 엔티티를 찾아 수정하고, 없으면 ELEMENT_NOT_FOUND다. id=null이면 패널마다 별도의 UUID를 생성한다. 요청 배열에서 빠진 기존 항목은 soft delete, 배열 순서로 readingOrder를 1부터 재부여한다.

따라서 같은 텍스트 id와 점자 id가 이미 있는 구 작업은 내용 수정·순서 변경·삭제가 가능하다. 새 블록을 각 패널에 null id로 보내면 두 패널의 id가 달라진다. 응답에는 새 id 매핑이 없어 클라이언트는 이를 안정적으로 재결합할 수 없다. 문서의 ‘점자 id는 텍스트와 짝’ 검증은 현재 `saveBraille` 코드에 없다.

V3.1 새 작업의 `braille_text_list=[]`는 더 직접적인 문제다. 앱이 기존 텍스트 id로 점자를 보내도 대응 BrailleElement가 없어 실패한다. 첫 로컬 점역 결과부터 서버에 온전히 저장하려면 백엔드 변경이 필요하다.

`JobSaveService`는 설정부터 저장하고 각 쪽 트랜잭션 실패를 `failedPages`로 모은다. 전 쪽 실패도 현재 코드는 savedPages=0인 정상 응답을 반환한다(문서의 COMMON5000과 다름). 앱은 HTTP 성공 여부만으로 저장 완료를 표시하면 안 된다. 메모는 쪽 전체를 교체하며 현재 구현은 memoId로 기존 생성 시각을 회수하지 않고 요청 createdAt을 직접 사용한다.

## 필요한 계약

1. 기존 텍스트 id로 새 점자를 저장할 때 같은 id로 BrailleElement를 생성한다.
2. 새 블록은 클라이언트 임시 id와 서버 id 매핑을 반환하거나, 클라이언트 UUID를 두 패널에 공통으로 허용하는 계약을 정한다. 임의의 위치·본문 비교로 짝을 추측하지 않는다.
3. 텍스트·점자·메모 연결 유효성을 쪽 트랜잭션 안에서 검증한다.
4. 삭제·재정렬·분할·재저장 테스트와 실제 신규 V3.1 작업의 첫 저장 통합 검증이 필요하다.

## 새 문서 미정

사용자는 빈 문서의 서버 생성 흐름을 이후 결정하도록 요청했다. 최신 API는 본문이 있는 텍스트를 AI로 보내 서버 쪽/블록을 만드는 방식이다. 빈 문서 생성과 저장 중 새 원본 쪽 추가 API는 없다. 앱의 새 문서는 로컬 초안으로 유지하며 저장을 AI 변환 호출로 바꾸지 않는다. 로컬 초안과 명시적 업로드/AI 변환을 잇는 최종 UX는 미정이다.
