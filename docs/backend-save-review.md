# 서버 저장 계약 검토와 수정 제안

2026-10-19 확인. 기준: [Semojum/BE 5d8dda0a](https://github.com/Semojum/BE/tree/5d8dda0a57f602a9ab7bc6f577d7bdb51bef8fc1). 운영 서버 배포 여부는 미검증이다. **사용자 결정에 따라 BE 코드는 수정하지 않았다.**

## 새 문서와 TXT 흐름 — 이전 미정 사항의 해소

최신 API는 `POST /api/jobs/text`로 빈 COMPLETED 작업을 생성한다. 텍스트를 AI에 보내지 않고 크레딧을 차감하지 않는다. 앱은 계정 기본 옵션·양식을 읽어 빈 작업을 만든 후 로컬에서 입력과 점역을 처리한다.

`PageContentSaver.savePage`는 페이지 결과가 없으면 `createTextPage`를 호출한다(46–95행). mode=b 텍스트 작업만 앱이 보낸 쪽 번호로 페이지를 만들며 결과 상태는 SAVED다. PDF/HWP/이미지의 없는 쪽을 임의로 만들지는 않는다. 따라서 ‘빈 문서 생성 API가 없다/저장으로 쪽을 추가할 수 없다’는 이전 문서 내용은 현재 코드에 해당하지 않는다.

## 아직 남아 있는 저장 결함

같은 파일의 `saveText`(101행부터)와 `saveBraille`(138행부터)는 독립된 ID 공간처럼 처리한다.

1. 기존 id는 해당 패널 테이블에서 찾아야 한다. 텍스트에만 존재하는 id로 첫 점자를 저장하면 BrailleElement가 없으므로 ELEMENT_NOT_FOUND다.
2. id=null은 패널마다 각각 UUID를 만든다. 텍스트와 점자에 같은 내용을 보낸다고 같은 id가 되지 않는다.
3. 저장 응답에는 생성된 블록 id 매핑이 없다. 본문·배열 위치로 재결합하면 중복 문장, 삭제, 재정렬에서 다른 블록과 연결될 수 있다.
4. 요청 배열에서 빠진 항목은 soft delete되고, 배열 순서로 readingOrder가 부여된다. 전체 스냅샷을 보내야 한다.
5. 저장은 쪽별 트랜잭션이다. HTTP 성공이 전 쪽 성공을 뜻하지 않으므로 앱은 savedPages·failedPages를 확인한다.

이미 텍스트·점자가 동일 id로 존재하는 구 작업의 편집·정렬·삭제는 가능한 계약이다. 새 작업의 첫 로컬 점자, 새 블록 추가·분할의 완전한 서버 동기화는 위 결함 때문에 완료로 표시하지 않는다. 앱은 먼저 원자적으로 `.smj`를 저장하고 서버 실패를 따로 알려 편집 내용을 보존한다.

## 제안 계약

- 기존 텍스트 id의 첫 점자를 저장할 때 같은 id로 BrailleElement를 upsert한다. 타 작업 id는 거부한다.
- 새 블록은 클라이언트 UUID를 두 패널에 공통으로 허용하거나, `clientId → textId/brailleId` 매핑을 반환한다. 재시도에도 동일 블록을 가리켜야 한다.
- 한 쪽 트랜잭션에서 텍스트·점자·메모 소속과 삭제를 검증한다.
- 메모는 `blockId`와 일치하는 패널/줄에 연결한다. 신규 메모 ID·생성 시각은 응답에서 반환한다. 로컬 해결 표시(resolved)를 서버에도 보존하려면 필드를 추가한다.
- 검증 시나리오: 빈 텍스트 작업 첫 저장, AI 작업 첫 점자 저장, 같은 내용 블록 2개, 중간 삽입, 삭제/복원, 병합/분할, 재정렬, 같은 저장 재전송, 쪽 일부 실패, 다른 계정 소속 id.

## Service 기획과 추가 확인이 필요한 계약

사용자는 서버 디렉토리·휴지통과 관리자 웹 콘솔을 후속 범위로 확정했다. 데스크톱에는 `POST /api/jobs/{jobId}/cancel`을 연결했다. JobController 144–152행의 취소는 처리 중인 쪽을 마무리하고 status로 확정하는 계약이다.

실패 쪽 사용자 AI 재시도, 로그인 잠금 정책의 실제 배포, PDF 암호 전달은 추가 확인이 필요하다. Worker 내부 자동 retry는 사용자 요청 API가 아니다. HWP 서식 반영 세부 옵션은 현 업로드 요청에 없다. 꼬리말의 면 범위·메모 resolved 상태도 저장 필드가 없어 `.smj`에만 남는다.
